## Critical Issues (Blocks Indexing or Causes Penalties)

### CRIT-1: Sitemap uses deprecated `priority` and `changefreq` tags across all 198 URLs

**Severity:** Critical (wasted signal — Google ignores both tags)
**Affected:** All 198 URLs in `/sitemap.xml`

Both `<priority>` and `<changefreq>` have been officially ignored by Google since 2023. They add 2× as many XML nodes as needed, inflating the sitemap file size and wasting crawl budget parsing noise.

**Current sitemap entry (example):**
```xml
<url>
  <loc>https://app.onchainworldcup.xyz/qualification/argentina</loc>
  <lastmod>2026-02-17T10:04:16.485Z</lastmod>
  <changefreq>daily</changefreq>
  <priority>0.5</priority>
</url>
```

**Fix — remove both deprecated tags:**
```xml
<url>
  <loc>https://app.onchainworldcup.xyz/qualification/argentina</loc>
  <lastmod>2026-02-17T10:04:16.485Z</lastmod>
</url>
```

**Source file:** `/apps/app/app/sitemap.ts`

---

### CRIT-2: 197 of 198 sitemap entries have identical `lastmod` timestamps

**Severity:** Critical (defeats lastmod's purpose; Google stops trusting it)
**Affected:** All entries except `/how-it-works` (which correctly uses `2026-02-16`)

Every URL except `/how-it-works` shares the exact timestamp `2026-02-17T10:04:16.485Z` — the server's boot time. This is generated by `new Date()` in `sitemap.ts`. When Googlebot sees 197 URLs with the same millisecond-precision timestamp, it correctly infers the dates are synthetic and discards `lastmod` entirely for the whole sitemap.

**Root cause in `/apps/app/app/sitemap.ts`:**
```ts
const now = new Date()
// ...
lastModified: now,  // Same timestamp for all 197 dynamic URLs
```

**Fix — use meaningful dates per category:**
```ts
const staticRoutes: MetadataRoute.Sitemap = [
  { url: baseUrl, lastModified: now, /* ... */ },
  { url: `${baseUrl}/qualification`, lastModified: now, /* ... */ },
  { url: `${baseUrl}/leaderboard`, lastModified: now, /* ... */ },
  { url: `${baseUrl}/tournament`, lastModified: new Date("2026-02-16"), /* ... */ },
  { url: `${baseUrl}/stats`, lastModified: now, /* ... */ },
  { url: `${baseUrl}/how-it-works`, lastModified: staticContentDate, /* ... */ },
]

// For country pages: use a fixed date since the template does not change daily
const countryContentDate = new Date("2026-02-16")
const qualificationRoutes: MetadataRoute.Sitemap = countriesData.map((country) => ({
  url: `${baseUrl}/qualification/${country.name.toLowerCase().replace(/\s+/g, "-")}`,
  lastModified: countryContentDate, // Template date, not server boot time
}))
```

### CRIT-3: 192 qualification country pages are thin-content template pages (quality gate WARNING)

**Severity:** Critical — doorway page risk
**Affected:** 192 URLs matching `/qualification/[countryId]`

**Quality Gate Triggered: WARNING (192 pages > 30-page threshold)**

Each country page contains approximately 99 words of visible text after stripping navigation, footer, and disclaimers. The meaningful unique content per page is approximately 15–20 words (the country name and flag). All 192 pages have identical structure, identical meta description patterns, and show "LOADING" placeholders for live vote data.

Content audit across 4 sample pages (Argentina, Brazil, France, Zimbabwe):

| Page | Word count | Unique words | Dynamic data shown in HTML |
|---|---|---|---|
| `/qualification/argentina` | ~99 | ~3 | None — "LOADING" placeholder |
| `/qualification/brazil` | ~99 | ~3 | None — "LOADING" placeholder |
| `/qualification/france` | ~99 | ~3 | None — "LOADING" placeholder |
| `/qualification/zimbabwe` | ~99 | ~3 | None — "LOADING" placeholder |

The pages load their data entirely client-side via React state. Google's indexing crawler sees only the "LOADING" placeholder — not the vote counts, rankings, or stats that would constitute meaningful content.

**Google's doorway page policy applies when:** a large set of pages exists with the same template where only one word changes per page and no meaningful unique content is served to the crawler.

**Mitigations to implement:**

Option A (recommended) — SSR or ISR the vote data for country pages:
```tsx
// apps/app/app/qualification/[countryId]/page.tsx
export async function generateStaticParams() { /* ... */ }

// Fetch real vote data at build/revalidate time
const voteData = await fetch(`/api/qualification/${countryId}/stats`)
// Render actual rank, vote count, ETH raised server-side
```

Option B — Add at least 200 words of country-specific static content per page (World Cup history, qualification record, notable players, confederation info).

Option C — Add `noindex` to all country pages except the top 48 qualifying countries. Keep only meaningful pages in the sitemap.

### HIGH-2: Duplicate BreadcrumbList schemas on all 192 country pages

**Affected:** All `/qualification/[countryId]` pages
**Impact:** Schema validator warnings; Google may use the wrong breadcrumb

Each country page renders two BreadcrumbList blocks:

- Block from `qualification/layout.tsx` (parent layout): `Home > Qualification` (2 items)
- Block from `qualification/[countryId]/page.tsx` (page): `Home > Qualification > [Country]` (3 items, but `item` field missing on position 3)

The correct 3-level breadcrumb is being rendered, but the 2-level duplicate from the parent layout is noise. Additionally, position 3 (the country itself) is missing its `item` URL — a required field for Google's breadcrumb rich result.

**Current broken state:**
```json
{
  "@type": "BreadcrumbList",
  "itemListElement": [
    { "position": 1, "name": "Home", "item": "https://app.onchainworldcup.xyz/" },
    { "position": 2, "name": "Qualification", "item": "https://app.onchainworldcup.xyz/qualification" },
    { "position": 3, "name": "Argentina" }
  ]
}
```

**Fix 1 — Remove BreadcrumbList from `qualification/layout.tsx`** (the parent layout should not inject it since child pages render their own).

**Fix 2 — Add `item` URL to position 3 in `qualification/[countryId]/page.tsx`:**
```tsx
{ "@type": "ListItem", "position": 3, "name": countryName, "item": `https://app.onchainworldcup.xyz/qualification/${countryId}` }
```

**Source file:** `/apps/app/app/qualification/[countryId]/page.tsx` and `/apps/app/app/qualification/layout.tsx`

**Affected:** `https://app.onchainworldcup.xyz/stats`
**Impact:** Google sees only "Loading statistics..." — zero indexable content

**Fix 2 (recommended)** — Convert stats page to a server component or use ISR with `revalidate: 60` so live numbers are crawlable.

### HIGH-5: Country page metadata has a title/OG title mismatch

**Affected:** All 192 `/qualification/[countryId]` pages
**Impact:** Inconsistent social sharing; Google may prefer OG title over `<title>`

The `<title>` and `og:title` are sourced from two separate metadata definitions (page.tsx vs layout.tsx) and are inconsistent in format:

- `<title>`: `Vote for Argentina 🇦🇷 | Onchain World Cup 2026`
- `og:title`: `🇦🇷 Argentina - World Cup 2026 Qualification`

This creates two different brand impressions depending on whether the link is clicked via Google (uses `<title>`) or shared on social (uses `og:title`).

**Root cause:** `qualification/[countryId]/layout.tsx` and `qualification/[countryId]/page.tsx` both export metadata independently.

**Fix — consolidate to a single `generateMetadata` in `page.tsx`** and remove the separate layout-level metadata export. Use consistent format:
```ts
title: `Vote for ${country.name} ${country.flagEmoji} | Onchain World Cup 2026`,
openGraph: {
  title: `Vote for ${country.name} ${country.flagEmoji} | Onchain World Cup 2026`,
  // ...
}
```

## Medium Priority Issues (Optimisation Opportunities)

### MED-1: CSP allows `frame-ancestors: *` — no clickjacking protection

**Affected:** All pages
**Impact:** Security posture; not a direct ranking factor but relevant to trust signals

The Content-Security-Policy header includes `frame-ancestors *`, which permits any domain to embed the app in an iframe. This is likely intentional for the Farcaster Mini App frame integration. However, `X-Frame-Options` header is absent — the CSP `frame-ancestors` directive supersedes it for modern browsers, but older crawlers and security scanners may flag it as a vulnerability.

**Recommendation:** If Farcaster framing requires `frame-ancestors *`, document this explicitly. If specific domains only (e.g. Warpcast), tighten to:
```
frame-ancestors https://warpcast.com https://app.onchainworldcup.xyz
```

---

### MED-2: OG images are large (227–235KB) with no `cache-control` max-age

**Affected:** All OG image routes
**Impact:** Social crawlers (Twitter/X, Facebook) must re-download on every share

OG images are served with:
```
cache-control: public, max-age=0, must-revalidate
```

At 227–235KB per image, this is acceptable in size but the `max-age=0` means every social crawler fetch hits the origin. Recommended for static OG images:
```
cache-control: public, max-age=86400, stale-while-revalidate=3600
```

For the country-specific images that should update when vote data changes, a 60-second `max-age` with ISR would suffice.

### MED-3: SportsEvent schema is missing `offers` field — reduces rich result eligibility

**Affected:** `/qualification` and `/tournament`
**Impact:** Cannot show ticket/participation price in rich results

The `SportsEvent` schemas on both pages omit the `offers` property, which is how Google surfaces pricing in search. While this is a blockchain voting app rather than a traditional ticketed event, an `Offer` describing the starting ETH price would improve rich result eligibility:

```json
"offers": {
  "@type": "Offer",
  "name": "Vote on Onchain World Cup",
  "description": "Vote with ETH starting at 0.001 ETH per vote",
  "price": "0.001",
  "priceCurrency": "ETH",
  "url": "https://app.onchainworldcup.xyz/qualification",
  "availability": "https://schema.org/InStock"
}
```

**Affected:** All pages

### LOW-4: OG image cache-busting tokens in URL (e.g. `?f8df7d0d4689e5cd`) are benign but permanent

**Affected:** All pages' `og:image` values
Next.js appends build-hash tokens to OG image URLs for cache invalidation. This is correct behaviour. However, each new deployment changes these tokens, meaning previously shared links with old hash values will need the social cache cleared. This is standard Next.js OG image behaviour.

---

### LOW-5: `how-it-works` `lastmod` is `2026-02-16T00:00:00.000Z` — UTC midnight

The static content date is set correctly to `2026-02-16`, but the ISO format includes the full timestamp `T00:00:00.000Z`. The W3C date format `YYYY-MM-DD` is sufficient and cleaner:
```xml
<lastmod>2026-02-16</lastmod>
```
